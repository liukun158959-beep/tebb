# 周时间轴与个人日程调整

状态：2026-10-22 用户已确认 Q1–Q8 全部推荐规则。独立交付单 [#138](https://github.com/liukun158959-beep/tebb/issues/138)，阶段总单 [#123](https://github.com/liukun158959-beep/tebb/issues/123)。

## 已定前提

- 继续使用飞书作为日程事实来源，复用已交付的 SchedulingService、事项关联、认证 RPC 和持久操作回执。
- 事项进度、截止日期、AI 执行状态分别管理；调整日程时间不改变这些状态。
- 交互原型用于确认布局；正式实现复用同一业务服务和认证 RPC，交付周时间轴、拖动已有日程改期和边缘调整时长，沿用现有看板风格。

## 事实约束

- 现有服务只提供单日读取及创建、关联、解除和创建结果核对，没有远端修改入口。原生 instance_view 可读取七天；复盘的摘要不能替代完整周数据。
- 当前“可关联”不证明“可编辑”，主日历可写也不证明任意事件可改。事件组织者和完整参与人需另外核对；instance_view 的参与人列表只有会议室，不能据其为空认定没有参与人。
- 本地 CLI calendar.events.patch 支持一起更新起止；need_notification 只说明 Bot 通知开关。当前 schema 没有幂等键、ETag 或条件版本，不能承诺飞书侧原子防覆盖。修改应只提交必要时间字段，不能复制创建时的空参会人、提醒和视频会议设置。
- 当前 470px 模态日程侧栏在看板拖拽上下文之外，周视图需要更宽的承载区域；卡片拖入创建还涉及共享拖拽作用域，须单独确定本批是否包含。
- 后续本地 schema 调查确认，参与人名单可能包含组织者本人；“没有任何参会人”与“只有自己、没有其他参与人”需要明确区别，因此补充 Q8，而不是在实现中静默排除本人行。完整参与人核对须显式分页至 has_more=false，不能把 CLI 自动分页的默认页数上限当成穷尽。

## 第一轮已确认（2026-10-22，Q1–Q3）

1. Q1 承载及本批范围：采用“独立周视图”，从现有日程安排入口进入较宽的周工作区，保留看板、单日快捷查看和事项双向定位。先交付已有日程拖动改期与调整时长，卡片拖入新建另批；“事项对照”仅为探索原型，不是本批交付布局。
2. Q2 时间视图：周一至周日、北京时间 UTC+8，默认 08:00–20:00，可切换完整 24 小时；时段外安排须有提示、可定位，窄窗口按选中日期展示，不挤压七列。全天、重复、跨日日程仍可见。
3. Q3 可编辑类型：先对自己组织、可核实有修改权且无其他参与人的普通单次同日日程开放操作，有无事项关联均可；归档事项沿用先恢复再调整。Q8 已明确名单中只有本人组织者仍符合“无其他参与人”。全天、重复、跨日及权限/完整参与人无法确认的记录先只读并说明原因，不因列表中未出现参与人就判断无人。多人会议及其通知、会议室规则另批。

## 第二轮已确认（2026-10-22，Q4）

- Q4 操作与保存：拖动正文保持原时长，拖动上下边缘调整起止，按 15 分钟吸附；缩放最短 15 分钟，已有更短日程仍可保持原时长移动。拖动中仅预览，松手提交一次保存；Escape、无效落点或时间未变化时不提交。表单仍明确保存，保留键盘等价及减少动效。正式实现采用松手保存并显示保存中及实际结果；此前原型的二次确认不再作为正式保存策略。

## 第二轮已确认（2026-10-22，Q5–Q7）
- Q5 时间边界与重叠：允许移到其他日期/周及 08:00–20:00 之外，开始结束仍须处于同一北京时间自然日；跨周用日期表单，不增加拖到边缘自动翻周。已结束日程先只读，进行中可调，目标结束须晚于当前时刻。与已读日程重叠只提示，不阻止保存，也不宣称覆盖所有忙闲；不改变事项截止日期。
- Q6 远端更改与失败：写入前重新核对身份、权限、完整参与人和原时间；已变化则展示最新值并要求用户重新调整，只修改同一事件的起止，不重建、不清空其他字段。远端修改成功与时间再次核对、缓存/关联/下一次安排更新分别回执；读取结果不同或无法读取时标明实际阶段，不误报完整成功。确认未写入才恢复已确认时间；超时、断连及结果不明保留原/拟调整时间和操作编号，不自动重发。重新读到旧值也不证明未执行，须结合操作生命周期核对。接口没有条件版本，修改前核对不能承诺远端原子防覆盖。
- Q7 并发、恢复与验收：操作期间同一事件及其关联事项拒绝冲突修改，读取、其他事项及 AI 继续；共享日历写资源冲突立即拒绝，不排队，网络等待不持数据库或全局写锁。不明结果仅暂停该事件时间写入及关联变更，普通事项编辑可继续；重连/重启先按持久编号读取，不自动重放。复用现有服务、回执、认证和调试入口，覆盖假飞书、隔离数据、认证 RPC、真实 UI 拖动/键盘、并发/故障/恢复和完整受影响层回归后提交，不发布。

本轮已作为交付边界确认，自主完成实现、验收和提交；仅在边界发生实质变化时再次澄清。不把原型试用当成需求签字，所有原型数据为示例，不连接飞书。

## 实现职责与复用

周工作区由 WorkBoardPane 承载，按需加载 ScheduleWeekPane；保留旧 SchedulePane 的新建、关联、解除与单日查看。周与单日演示共用 createScheduleDemo，真实运行共用 SchedulingService，不新增平行日历或日程存储。FullCalendar 6.1.22 的 React、timegrid、interaction 插件负责时间网格、重叠布局及指针拖动，luxon3 插件明确使用 Asia/Shanghai，避免浏览器系统时区影响。版本统一锁定，未引入另一个事项拖拽框架。

ScheduleWeekController 拥有按事件的执行与未确认标记、读取版本和编辑资格快照；组件拥有当前日期、表单和手势预览。标记在发送前保存在本机，包含编号和起止时间，不包含 token、标题或正文。回执、事项关系及日/周缓存仍由 SchedulingService 管理。cache_event 统一刷新已加载的日期范围和关联，阻止旧读取覆盖确认结果；纯日期、资格和时长规则归 schedule_domain/calendar_time，原生 CLI 协议归 CalendarAdapter。详见 [ADR 0018](adr/0018-personal-calendar-time-edit.md)。

## 恢复与限制

未确认改期一直使用原事件身份。当前值等于旧值、目标值或第三个值都不能单独证明原执行结果；显式核对只登记当前观察值，并在事件预留内封存原请求，不发送 PATCH。不明操作仍在执行时不能结束核对。已明确删除/不存在必须再次确认该状态，普通读取失败或权限不足不能当作删除。事项的普通编辑在执行收尾后可继续，关联变更和再次改期则先完成原事件核对。

参与人核对最多 20 页、合计约 35 秒，每条 CLI 调用最长 20 秒，无法穷尽时保持只读；同步 RPC 等待 120 秒，超时后台可能继续。本机标记损坏时保留原记录并暂停新改期，先检查操作回执。真实飞书没有条件版本，读取后到 PATCH 前仍可能发生外部修改；不承诺原子防覆盖。need_notification=false 不等于所有渠道绝不产生通知，因此本批仅允许已验证没有其他参与人的个人日程。

主样本来自当前便携版的数据目录：5 条主任务、12 个执行阶段、27 次有阶段关联的模型 HTTP 调用，另有 26 段工具等待。27 次 HTTP 记录均完整结束；这不等于语义交付全部正确。源码目录混有大量本地测试记录，不与主样本合并；这组数据不是随机评测集。

| 环节 | 段数 | 累计耗时 | 占阶段累计时间 | 单段中位数 / 最大值 |
| --- | ---: | ---: | ---: | --- |

按 HTTP 阶段：聊天 1 次为 2.98 秒；路由 7 次中位数 12.17 秒、最大 39.39 秒；执行 19 次中位数 11.34 秒、最大 52.77 秒。执行调用累计 320.69 秒，路由累计 107.21 秒，是主要投入。

实际 HTTP 发送至结束合计 430.88 秒，其中响应头之后约 391.35 秒，约占全部阶段累计时间 70%。响应头之前合计约 39.52 秒；其内含连接、发送与服务端等待，不能全算网络连接。日志不能进一步严格区分服务端排队、推理、参数/正文生成和传输，不能据此断言某个供应商内部环节的精确比例。

首段可见正文仅对有文本标记的调用统计：路由 2 个样本为 2.28–12.46 秒；执行 10 个样本中位数 5.32 秒、最大 31.52 秒。其余调用可能只输出结构化工具参数，缺少文字不算零耗时。任务时钟与 HTTP 记录有不同边界，不能直接相减当作单一瓶颈。前端每 400ms 轮询，未采集真实用户窗口的逐帧耗时；本次浏览器回归只验证显示连续性。

## 已落实的优化

Atlas 延迟加载 SDK 后，一次性待命 worker 仅预载 collaboration_worker 和 HTTP 初始化，没有加载 collaboration_llm 的 OpenAI/Pydantic 依赖。因此实际记录中即便标记 prewarmed，仍有数秒准备开销。

现将适配器导入移到待命就绪之前，不发送模型请求，不绑定用户任务，不扩大进程池或改变预算。成本提前到明确记录的后台预热阶段；冷启动和来不及补充待命进程时仍需承担准备成本。

使用发布包 Python 3.13.16 加载当前源码、相同本地 SSE 假模型，各 5 个串行样本，7 秒间隔保证一次性待命进程补齐：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 用户请求准备中位数 | 2331ms | 77ms |
| 首段文字中位数 | 3782ms | 1699ms |
| 请求总耗时中位数 | 4156ms | 2056ms |
| 后台预热时间 | 1.23 秒 | 2.78 秒 |
| 成功 / 超时 | 5 / 0 | 5 / 0 |

这是应用开销对照，不代表真实模型生成速度变快；样本不足，P95/P99 均不宣称达标。不会靠答案缓存或重复执行工具来提高数字。

## 下一步优化顺序

1. 先用 #173 的任务质量样本评估路由开销：区分普通聊天、目标补充、明确执行和真正需要分工的任务，减少没有收益的重复路由；不能靠关键词强行把复杂请求当简单任务。
2. 对响应流长尾及推理/工具参数生成单独测量；如调整阶段的思考策略或模型，需要明确能力和质量对照，不悄悄替换模型。
3. 在 #168/#170 中统一上下文选择与阶段预算，减少重复材料和无收益的工具往返；每项以成功率、错误交付、成本和耗时一起判断。
4. 工具在此样本只占约 5.5%，优先解决最慢工具和重复请求，再考虑已有只读能力的并行；远端写入不自动重试。

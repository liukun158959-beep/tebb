# 模型连接与性能验证

设置 → 模型请求网络：系统代理、直连、自定义代理三选一。支持HTTP、HTTPS、SOCKS5；账号密码分开填写，密码不返回前端。留空保留已有密码，勾选可清除。直连/自定义不读取系统代理，继续校验TLS并保留配置的CA信任根，不修改全局环境。设置用于后续模型调用；网页搜索、平台登录、飞书CLI仍使用各自的网络设置。配置保存在不入库的 `model-network.json`。

浮窗右上角统一使用18px SVG、28px居中点击区域；新对话使用当前伙伴，保留原会话草稿和进行中的任务，失败重试沿用去重编号。

## 性能约定

- 简单问候仍真实调用用户选择的模型。不用固定台词、答案缓存或暗中换模型冒充更快。
- 聊天队列保持一个待命的一次性进程。后台仅预加载依赖和传输层，收到请求才调用模型；每个进程只执行一项请求然后退出。待命未就绪或失效时回退普通冷启动；取消和退出仍结束所属进程树。预热在启动阶段异步进行，不等于首次启动没有成本。
- 一项执行任务内部复用HTTP连接，工具白名单、进程隔离、权限、调用预算和总截止时间不变。不会因模型慢而重复已执行工具，也不关闭TLS校验。
- 调试窗口「耗时分析」根据实际事件和HTTP边界显示瓶颈，详见 [Agent调试](AGENT_DEBUG.md)。

## 可重复测试

从仓库根目录运行。默认的本地固定SSE仅验证应用自身开销，不代表模型性能；每个样本仍经过真实持久队列和独立工作进程。

```powershell
python scripts/benchmark_agent.py --samples 100 --parallel 1 --prewarm --think-time 5 --output memory/performance/local.json --check
python scripts/benchmark_agent.py --live --samples 100 --parallel 2 --mode direct --output memory/performance/live.json --check
```

`--live`会真实调用当前激活模型并计入用量。`--mode configured`沿用已保存的网络配置，`system/direct`只覆盖隔离基准，不更改客户端偏好。每个基准使用独立临时数据目录，不读取聊天历史、不调用工具、不写飞书；结束后关闭工作进程并清理模型与代理配置副本。JSON只保留指标、模型名和网络方式，不含模型Key或代理凭据。

`--parallel`是封闭循环并发，不是持续高并发压力测试。`--think-time`是请求之间的间隔，不计入单次请求延迟，适合验证交互时的待命补充；省略时可观察连续突发请求的冷启动回退。预热耗时、预热命中数、并发数、间隔都单独记录，不排除冷启动慢样本。退出码为非零表示门槛未通过或样本不足，不能把测试执行完当成性能达标。

百分位使用nearest-rank。P99需要至少100个有效观测，P95需要20个；失败/超时计入整体耗时和失败率，超时是到截止时间的观测，不代表若继续等待的实际完成时间。首段文字仅统计成功且有该测量的请求，缺失不填0。默认门槛：本地固定SSE总耗时P99≤5秒、首段P99≤4.5秒；真实模型总耗时P99≤30秒、首段P99≤15秒；进程准备P99≤3.5秒且零失败。门槛与样本量写入报告，未满足不宣称通过。预热模式的指标不代替首次启动或持续突发负载指标。

## 2026-10-16 实测

| 场景 | 样本和网络 | 实际结果 |
| --- | --- | --- |
| 开发阶段冷进程基线 | 100次真实 `glm-5.3-flash`，直连，2路并发，40秒调用等待限额 | 93成功、7超时；总耗时P50 9.80秒、P95 42.60秒、P99 43.20秒。进程准备P99 3.92秒。未达标。 |
| 预热真实回归 | 10次同模型，直连，1路并发，无请求间隔 | 10次均命中待命进程；准备中位数67.77毫秒、最大97.45毫秒，回复总耗时中位数5.27秒；9成功、1超时。样本不足，不给P99。 |
| 应用开销回归 | 100次本地固定SSE，1路并发，5秒请求间隔 | 100成功、零超时，99次命中预热；总耗时P99 3.53秒、最大7.81秒，首段P99 3.28秒，准备P99 0.489秒、最大5.45秒；预热初始成本4.03秒单独报告。既定本地门槛通过，不代表真实模型通过。 |

冷进程基线用于定位问题，采集期间同步迭代了诊断代码，不作为固定发布构建的正式性能基线。预热真实回归同样不能证明与不同并发基线的整体提升比例。7次基线超时均已完成TCP连接、TLS及请求发送，在等待响应头时达到截止时间；未收到可见文字。连接/握手合计约0.13～0.19秒，主要长尾位于请求发出后的上游响应阶段，不能从客户端判定上游网络、中转或模型服务内部谁负责。

因此目前只能确认客户端准备开销已降低，**当前模型接口的端到端P99和成功率尚未达标**。更换网络策略并不能保证消除该长尾；需要继续验证上游服务或经用户选择的其他模型，不能通过只统计成功请求、放宽门槛、伪造即时回复来宣称通过。

本机客户端真实RPC回归也已验证：一次问候命中预热，准备约50毫秒、实际调用模型一次；系统代理方式下整条请求仍用时约37.66秒，调试窗口对应任务、HTTP阶段和网络设置回读均正确，原有会话未改动。上游长尾继续跟踪 [Issue #97](https://github.com/liukun158959-beep/tebb/issues/97)。功能回归为前端97项通过、后端相关131项中130项通过且1项环境跳过；另有针对进程关闭与网络验证的回归通过。未进行原生UI自动化或发布新安装包。


后续交互与工具回归修复了目录预检、路由重复生成、GLM工具上下文、函数参数流进展、共享时限及编码命令等待，见[2026-10-16工具回归](TOOL_REGRESSION_20261016.md)。其中单次真实编码闭环成功不改变上述P99未达标结论。
